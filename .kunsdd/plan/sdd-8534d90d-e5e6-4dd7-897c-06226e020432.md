# Kun Mobile — Phase 1 MVP Implementation Plan

## Summary

Build the Phase 1 MVP of **Kun Mobile**, a React Native (Expo) companion app for the Kun desktop agent. The desktop-side Gateway service and session management core are already implemented (`mobile-gateway.ts`, `mobile-session.ts`, `mobile-api-types.ts`). This plan covers the remaining desktop integration (settings, IPC, main-process wiring, Settings UI) and the full Expo mobile app (scaffold, API client, SSE event processing, screens, components).

---

## Current State Assessment

### Already implemented (verified in codebase)
- `src/main/mobile-gateway.ts` — `MobileGateway` class: HTTP proxy on `0.0.0.0`, Bearer token auth, whitelist check, `/mobile` prefix strip, SSE `res.pipe(res)` pass-through, dynamic port allocation, Kun `/health` probe before start
- `src/main/mobile-gateway.test.ts` — 9 tests covering start, auth (401, revoked token), whitelist (404), prefix stripping, SSE streaming, stop/idempotency
- `src/main/mobile-session.ts` — `createSession`, `validateToken`, `revokeSession`, `refreshToken` using `crypto.randomUUID()`
- `src/main/mobile-session.test.ts` — 12 tests covering session CRUD, token validation, revocation, refresh immutability
- `src/shared/mobile-api-types.ts` — `MobileSessionV1`, `ThreadDTO`, `TodoDTO`, `ApprovalDTO` DTOs

### NOT yet implemented
- **Settings schema**: `mobile.sessions` / `mobile.gatewayEnabled` fields missing from `AppSettingsV1` and normalizers
- **Main-process wiring**: Gateway not started/stopped from `index.ts`; no lifecycle hooks
- **IPC layer**: No mobile-related IPC channels in `app-ipc-schemas.ts` or `register-app-ipc-handlers.ts`
- **Settings UI**: No "连接手机" section component; no sidebar entry
- **Mobile app**: No `mobile/` directory — entire Expo project needs creation

## Pre-mortem

### Tigers (real risks)

| Risk | Severity | Mitigation | Owner | Decision Date |
|---|---|---|---|---|
| **SSE events through Gateway lose `content-type` or `transfer-encoding` headers** — the current `proxyRes.pipe(res)` forwards headers as-is, but some proxies/browsers may strip chunked encoding for SSE | Launch-Blocking | Add integration test: start real Gateway → open SSE → verify multi-event delivery including `assistant_text_delta` and `approval_requested` in sequence. If pipe drops headers, explicitly set `content-type: text/event-stream` and `cache-control: no-cache` on the proxy response. | Desktop dev | Before Phase 1 ship |
| **Expo managed workflow doesn't support `@microsoft/fetch-event-source`** — ReadableStream polyfill may be incomplete on older Expo SDKs | Fast-Follow | Pin Expo SDK 51+ (verified ReadableStream support). Fallback: use native `fetch` with manual SSE line parsing via `response.body.getReader()`. | Mobile dev | Week 1 |
| **Gateway port conflicts with firewall or VPN** — `0.0.0.0` binding may be blocked | Track | Document: "Ensure LAN connectivity; if blocked, use Tailscale/Cloudflare Tunnel." Gateway already probes Kun health before starting; add a Settings tooltip explaining network requirements. | — | — |
| **iOS background kills SSE within 30s** — Phase 1 doesn't have push notifications | Fast-Follow | Document known limitation. Add clear "Disconnected — pull to refresh" UX. Phase 3 adds APNs. | — | — |

### Paper Tigers
- **Token leakage in logs**: `mobile-gateway.ts` already logs only HTTP method/path/status, never the Authorization header. No action needed.
- **Gateway DDoS from LAN**: Phase 1 assumes trusted LAN. Rate limiting is a Phase 3 concern.

### Elephants
- **Kun API response shapes differ from `mobile-api-types.ts` DTOs**: The DTOs in `mobile-api-types.ts` are simplified. The mobile app must consume the raw Kun API responses (which are richer — see `CoreThreadSummaryJson` in `kun-contract.ts`). Investigation needed: either enrich the shared DTOs or have the mobile app use its own types derived from the actual API responses.

## Implementation Steps

### Step 1: Settings Schema — Add mobile config to AppSettingsV1

**Files to modify:**
- `src/shared/app-settings-types.ts` — Add `MobileSettingsV1` interface and field to `AppSettingsV1`
- `src/shared/app-settings.test.ts` — Add normalization tests for mobile settings

**Concrete changes:**

1. Define `MobileSessionV1` (already in `mobile-api-types.ts`) — no duplication needed, import it.

2. Add to `AppSettingsV1`:
```typescript
mobile?: {
  gatewayEnabled?: boolean
  sessions?: MobileSessionV1[]
}
```

3. Add default normalizer in the existing `normalizeAppSettings()` function:
```typescript
mobile: {
  gatewayEnabled: raw?.mobile?.gatewayEnabled === true,
  sessions: Array.isArray(raw?.mobile?.sessions) ? raw.mobile.sessions : []
}
```

4. Add tests: default mobile settings normalize to `{ gatewayEnabled: false, sessions: [] }`; existing sessions survive round-trip.

### Step 2: IPC Schema + Handlers — Bridge renderer ↔ main for mobile operations

**Files to modify:**
- `src/main/ipc/app-ipc-schemas.ts` — Add Zod schemas for mobile IPC channels
- `src/main/ipc/register-app-ipc-handlers.ts` — Register handler implementations

**New IPC channels:**

| Channel | Direction | Purpose |
|---|---|---|
| `mobile:getStatus` | renderer → main | Returns `{ gatewayEnabled, port, sessions, lanIp }` |
| `mobile:startGateway` | renderer → main | Starts Gateway, returns `{ port }` |
| `mobile:stopGateway` | renderer → main | Stops Gateway |
| `mobile:createSession` | renderer → main | Creates new session with name, returns `MobileSessionV1` |
| `mobile:refreshToken` | renderer → main | Refreshes token for session id, returns updated session |
| `mobile:revokeSession` | renderer → main | Revokes session by id |
| `mobile:getLanIp` | renderer → main | Returns the machine's LAN IP address |

**Implementation notes:**
- `mobile:startGateway` must: load sessions from settings → instantiate `MobileGateway` → call `gateway.start()` → persist `gatewayEnabled: true` → update settings → return port
- `mobile:stopGateway` must: call `gateway.stop()` → persist `gatewayEnabled: false`
- `mobile:getLanIp` uses `os.networkInterfaces()` to find the first non-internal IPv4 address
- Handlers follow existing pattern: Zod parse input, call service, Zod parse output

**Tests:**
- `app-ipc-schemas.test.ts` — Add schema validation tests for each new channel
- `register-app-ipc-handlers.test.ts` — Add integration tests for start/stop/create/revoke flows

### Step 3: Main-Process Lifecycle — Wire Gateway into app startup/shutdown

**Files to modify:**
- `src/main/index.ts` — Add Gateway lifecycle management

**Concrete changes:**

1. After Kun runtime starts and `settings-store` is ready, read `mobile.gatewayEnabled` from settings.
2. If enabled, load `mobile.sessions`, instantiate `MobileGateway`, call `start()`.
3. Store the gateway instance on the app state (similar to how `clawRuntime` or `scheduleRuntime` are managed).
4. On `app.on('before-quit')`, call `gateway.stop()`.
5. Expose gateway instance to IPC handlers (dependency injection pattern — pass to `registerAppIpcHandlers`).

**Test coverage:**
- `index.test.ts` — Mock settings with `gatewayEnabled: true`, verify Gateway is started on app ready and stopped on quit.

### Step 6: Mobile API Client Layer

**File: `mobile/src/api/client.ts`**

```typescript
// Core HTTP client — all requests go through here
// Reads baseUrl and token from connection store
// Adds Authorization: Bearer <token> header
// Handles 401 → clear token, navigate to settings
// Handles network errors → set disconnected state
```

**File: `mobile/src/api/sse.ts`**

SSE manager class:
- Opens `GET /mobile/v1/threads/{id}/events` with `Accept: text/event-stream`
- Uses `response.body.getReader()` + manual SSE line parsing
- Emits parsed events to the events store
- Auto-reconnect with exponential backoff (1s → 2s → 4s → ... → 30s max)
- `AppState` listener: on `change === 'active'`, reconnect if disconnected
- Exposes `connect(threadId, sinceSeq)`, `disconnect()`, `isConnected`

**File: `mobile/src/api/threads.ts`**
- `listThreads()` → `GET /mobile/v1/threads`
- `getThread(id)` → `GET /mobile/v1/threads/{id}`
- `getThreadTodos(id)` → `GET /mobile/v1/threads/{id}/todos`

**File: `mobile/src/api/approvals.ts`**
- `submitApproval(id, decision)` → `POST /mobile/v1/approvals/{id}` with `{ decision: 'allow' | 'deny' }`

**File: `mobile/src/api/user-inputs.ts`**
- `submitUserInput(id, answers)` → `POST /mobile/v1/user-inputs/{id}`

**File: `mobile/src/api/turns.ts`**
- `sendMessage(threadId, text)` → `POST /mobile/v1/threads/{id}/turns` with `{ message: text }`

**Tests:** Each API function tested with mock fetch, verifying correct URL, headers, body, error handling.

### Step 7: Mobile SSE Event Processing

**File: `mobile/src/store/events.ts`**

Port the SSE event dispatch logic from `src/renderer/src/agent/kun-mapper.ts` (`dispatchKunRuntimeEvents`) to mobile. The mobile version is simpler — no approval auto-approve/never logic (all approvals shown to user).

**Event kinds to handle (from kun-mapper.ts lines 1140-1260):**

| Event kind | Mobile behavior |
|---|---|
| `turn_started` | Mark thread as running |
| `assistant_text_delta` | (Phase 1: ignore; Phase 2: stream text) |
| `assistant_text` | Append to chat blocks |
| `tool_call_ready` | Append tool block to chat |
| `tool_call_finished` | Update tool block status |
| `approval_requested` | Add to approval queue, show ApprovalCard |
| `user_input_requested` | Show UserInputCard |
| `user_input_resolved` | Dismiss UserInputCard |
| `todos_updated` | Update todo list |
| `todos_cleared` | Clear todo list |
| `usage` | Store usage snapshot |
| `turn_completed` / `turn_aborted` | Mark thread idle |
| `turn_failed` | Show error in thread |
| `error` | Show error toast |

**Data structures (simplified from renderer's `types.ts`):**

```typescript
type ChatBlock =
  | { kind: 'user_message'; id: string; text: string; timestamp?: string }
  | { kind: 'agent_message'; id: string; text: string; timestamp?: string }
  | { kind: 'tool'; id: string; toolName: string; status: string; summary?: string }
  | { kind: 'error'; id: string; message: string; severity: string }

type Approval = {
  id: string
  summary: string
  toolName?: string
  status: 'pending' | 'approved' | 'denied'
}

type UserInputRequest = {
  id: string
  prompt?: string
  questions?: Array<{ id: string; header: string; question: string; options: Array<{ label: string; description: string }> }>
}
```

### Step 13: Error Handling — Mobile Client

**Implement in `mobile/src/api/client.ts` and screen-level catch blocks:**

| Scenario | Detection | UX |
|---|---|---|
| Gateway unreachable | `fetch` throws `TypeError: Network request failed` or timeout | Full-screen "无法连接到桌面端" with retry button and settings link |
| 401 Unauthorized | Response status 401 | Clear stored token, redirect to settings, toast "Token 无效，请重新输入" |
| SSE disconnect | ReadableStream ends or error event | StatusBar shows "重连中...", exponential backoff reconnect (1s→30s max) |
| Foreground resume | `AppState` change to `active` | Immediately reconnect SSE + refresh thread list |
| API 5xx | Response status ≥ 500 | Toast "服务异常，请稍后重连" |
| API 404 | Response status 404 | Should not happen in normal flow; log + show generic error |

## Risks & Open Questions

1. **DTO alignment**: `mobile-api-types.ts` DTOs (`ThreadDTO`, `TodoDTO`, `ApprovalDTO`) are simplified versions. The actual Kun API returns richer objects (e.g., `CoreThreadSummaryJson` has `titleAuto`, `pinned`, `goal`, `todos`, `relation`, etc.). **Decision**: The mobile app should define its own extended types based on actual API responses, importing only `MobileSessionV1` from shared. The existing `ThreadDTO`/`TodoDTO`/`ApprovalDTO` can be kept as reference but the mobile app will need richer types.

2. **Approval request body format**: The existing `POST /v1/approvals/{id}` endpoint expects `{ decision: 'allow' | 'deny' }` based on `kun-runtime.ts` `submitApprovalDecision`. Verify this matches the Kun API contract.

3. **User input response format**: `POST /v1/user-inputs/{id}` expects `{ answers: UserInputAnswer[] }` based on `submitUserInputResponse`. Need to verify the exact shape from the Kun API.

4. **Expo Go compatibility**: Some features (like `expo-notifications` for Phase 3) require a dev build. Phase 1 with basic fetch/SSE should work fine in Expo Go.

5. **TypeScript path sharing**: The mobile app references `../../src/shared/mobile-api-types.ts` from its `types/api.ts`. This works in development but may need attention for EAS Build. Consider a build-time copy step or a workspace package if the cross-referencing causes issues.
